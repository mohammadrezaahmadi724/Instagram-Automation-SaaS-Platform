# تصمیم‌های معماری

وضعیت سند: پیش‌نویس فاز ۱ب

تاریخ: 1405/09/04

تاریخ در مستندات شمسی است. در کد، دیتابیس و API، تاریخ ISO 8601 و UTC است.

`ADR-001`، `ADR-002`، `ADR-003`، `ADR-009`، `ADR-011`، `ADR-012`، `ADR-014`، `ADR-015` و `ADR-017` وضعیت `Accepted` دارند. ADR-001، ADR-002، ADR-003، ADR-012 و ADR-015 در نقشه‌ی راه `انجام‌شده` (Accepted و بازبینی‌شده) هستند. ADR-004، ADR-005، ADR-006، ADR-007، ADR-008، ADR-010، ADR-013 و ADR-016 همچنان `Proposed` هستند. نسخه‌های پکیج اسکلت در ADR-017 قفل شده است. وجود نام متغیر در `.env.example` برای ADRهای Proposed به‌معنای انتخاب آن ابزار نیست.

تصمیم‌گیرنده‌ی ADRهای Accepted این فاز: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات. بقیه‌ی ADRها همچنان با تصمیم مالک و پیشنهاد ATLAS باز هستند.

## قالب ADR

برای ADR بعدی همین قالب کپی می‌شود.

```
## ADR-XXX: <عنوان>
- وضعیت: Proposed | Accepted | Rejected | Superseded by ADR-YYY
- تاریخ: YYYY/MM/DD (شمسی)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS
### زمینه
### گزینه‌ها (حداقل ۲ گزینه، با مزایا و معایب)
### تصمیم
### پیامدها (فنی، امنیتی، هزینه، زمان)
### معیار بازبینی
```

## ADR-000: فاز ۰ فقط مستندات است و هیچ Stack انتخاب نشده

- وضعیت: Superseded by ADR-001
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS

فاز ۰ تمام شد و Stack در ADR-001 انتخاب شد. پذیرش اولیه‌ی این ADR در ۱۴۰۵/۰۹/۰۴ بود.

### زمینه

پروژه تازه شروع شده است. محدودیت محصول، API و امنیت باید قبل از کد ثبت شود. انتخاب تکنولوژی در همین مرحله، بدون ADR، بعداً خودش را به معماری تحمیل می‌کند.

### گزینه‌ها

1. شروع هم‌زمان مستندات و کد با یک Stack فرضی
   - مزیت: ظاهر شروع پیاده‌سازی زودتر است.
   - عیب: Stack بدون ADR ثابت می‌شود و با محدوده‌ی فاز ۰ ناسازگار است.
2. فاز ۰ فقط مستندات، قوانین و فایل‌های پایه‌ی مخزن، بدون کد و بدون نصب
   - مزیت: تصمیم معماری بعداً با ADR ثبت می‌شود و محدوده قابل بازبینی می‌ماند.
   - عیب: هنوز نرم‌افزار قابل اجرا وجود ندارد.

### تصمیم

فاز ۰ فقط مستندات، قوانین Cursor، و فایل‌های پایه‌ی مخزن است. هیچ Stack، دیتابیس، فریم‌ورک، یا کد اپلیکیشن انتخاب یا ایجاد نشده است.

### پیامدها

- فنی: مخزن کد اجرایی ندارد.
- امنیتی: سطح حمله‌ی اپلیکیشن هنوز وجود ندارد. الزامات امنیتی سندی‌اند و تست‌شان اجرا نشده است.
- هزینه: هزینه‌ی زیرساخت در این فاز صفر است.
- زمان: پیاده‌سازی تا Accepted شدن ADRهای فاز ۱ شروع نمی‌شود.

### معیار بازبینی

وقتی `ADR-001` تا `ADR-014` تعیین تکلیف شوند، جمله‌ی «Stack انتخاب نشده» دیگر وصف وضعیت جاری نیست. ممنوعیت تغییر معماری بدون ADR باقی می‌ماند. جایگزینی این ADR فقط با ADR جدید انجام می‌شود.

## ADR-001: Stack

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

مالک Stack را `Next.js` + `Node.js` + `PostgreSQL` انتخاب کرده است. این ADR جزئیات زبان، فریم‌ورک، ORM و ابزار کیفیت را ثبت می‌کند. نسخه‌ی دقیق پکیج‌ها اینجا قفل نمی‌شود. پرامپت 01b نسخه‌ی پایدار روز را بررسی و قفل می‌کند. اسکلت کد در همین تسک ساخته نمی‌شود.

### گزینه‌ها

1. `TypeScript` سخت‌گیر، `Next.js` با App Router، `Prisma`، `pnpm`، و ابزارهای تست و کیفیت فهرست‌شده در تصمیم
   - مزیت: یک زبان در فرانت و سرور، schemaی قابل‌بازبینی، و type safety از ورودی تا دیتابیس.
   - عیب: سطح یادگیری Next.js و مرز Server Component و Route Handler باید در 01b رعایت شود.
2. همان Stack، با `Drizzle` به‌جای `Prisma`
   - مزیت: نزدیکی به SQL، سبکی، و تعریف RLS در خود schema.
   - عیب: migration و ابزار بازبینی برای این تیم کم‌بلوغ‌تر است. این گزینه رد می‌شود.

### تصمیم

- زبان: `TypeScript` در حالت `strict` با `noUncheckedIndexedAccess` و `exactOptionalPropertyTypes`. `any` بدون توضیح ممنوع است.
- فرانت و BFF: `Next.js` آخرین نسخه‌ی پایدار، `App Router`، React Server Components به‌عنوان پیش‌فرض، و Server Actions برای mutationهای فرم. Route Handlers روی runtime `nodejs` برای webhook و APIهای عمومی استفاده می‌شوند. runtime `edge` برای مسیرهایی که secret یا دیتابیس دارند ممنوع است.
- Runtime: `Node.js` خط LTS فعال (حداقل 22، ترجیحاً 24 LTS).
- Package manager: `pnpm` با workspaces.
- ORM: `Prisma`. دلیل: schema خوانا برای بازبینی ناظر، migration بالغ و قابل‌ردیابی، type safety کامل، و آشنایی بالای ابزارهای AI که خطای تولید کد را کم می‌کند. جداسازی tenant در لایه‌ی repository انجام می‌شود، نه فقط با ORM. جزئیات در ADR-002 است.
- اعتبارسنجی: `zod` برای همه‌ی ورودی‌ها، چه سمت سرور و چه فرم‌ها.
- تست: `Vitest` برای unit و integration، `Testing Library` برای کامپوننت، `Playwright` برای e2e، و `@axe-core/playwright` برای دسترس‌پذیری.
- کیفیت کد: `ESLint` با تنظیمات Next و `typescript-eslint` در حالت strict، `Prettier`، و typecheck در CI.

### پیامدها

- فنی: فاز ۱ب اسکلت را با همین ابزارها می‌سازد. هر کتابخانه‌ی اصلی دیگر به ADR نیاز دارد.
- امنیتی: runtime `edge` به secret و دیتابیس نمی‌رسد. اعتبارسنجی ورودی با `zod` از همین تصمیم الزامی است.
- هزینه: ابزارهای نام‌برده در این فهرست هزینه‌ی سرویس ابری جدا ندارند. میزبانی هنوز ADR-004 است.
- زمان: تا تأیید ناظر روی این ADR، اسکلت 01b شروع نمی‌شود.

### معیار بازبینی

اگر نسخه‌ی پایدار Next.js یا Node LTS مدل App Router یا پشتیبانی Prisma را بشکند، یا اگر migrationهای Prisma برای RLS عملی نباشد. بازبینی RLS در ADR-002 آمده است.

## ADR-002: دیتابیس و multi-tenancy

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

محصول چندمستأجره است. `SEC-009` می‌گوید هر رکورد tenant-owned به `workspace_id` تعلق دارد، کوئری‌ها فیلتر tenant می‌شوند، و تست نشت در CI الزامی است. موتور دیتابیس را مالک `PostgreSQL` انتخاب کرده است. نسخه‌ی دقیق در 01b قفل می‌شود.

### گزینه‌ها

1. یک دیتابیس و یک schema مشترک، با ستون `workspace_id`، فیلتر در repository، و Postgres Row-Level Security
   - مزیت: یک مسیر migration و پشتیبان‌گیری. RLS لایه‌ی دوم است اگر کوئری فیلتر را جا بیندازد.
   - عیب: انزوا به درستی repository و policy وابسته است و باید با تست نشت ثابت شود.
2. schema جدا برای هر tenant
   - مزیت: مرز داده از اشتراک جدول خام جدا می‌شود.
   - عیب: پیچیدگی migration و هزینه در این مقیاس. این گزینه رد می‌شود.
3. دیتابیس جدا برای هر tenant
   - مزیت: مرز عملیاتی قوی‌تر است.
   - عیب: پیچیدگی migration و هزینه در این مقیاس. این گزینه رد می‌شود.

### تصمیم

- `PostgreSQL` خط پایدار فعلی (حداقل 16).
- مدل tenancy: یک دیتابیس و یک schema مشترک، با ستون `workspace_id` در همه‌ی جدول‌های tenant-owned.
- لایه‌ی اول: همه‌ی دسترسی‌ها از repository/service عبور می‌کنند و `workspace_id` را از نشست سرور می‌گیرند، نه از ورودی کاربر.
- لایه‌ی دوم (defense in depth): Postgres Row-Level Security روی جدول‌های tenant-owned، با `set_config('app.workspace_id', …)` داخل تراکنش. پیاده‌سازی RLS در فاز ۳ است و اگر عملی نبود، با ADR جدید بازبینی می‌شود.
- تست نشت داده بین tenantها در CI الزامی است (`SEC-009`).
- کلید اصلی: `uuid` نسخه‌ی 7 یا `cuid2`. انتخاب نهایی در 01b. شناسه‌ی عددی ترتیبی در URL ممنوع است.
- زمان: `timestamptz` به UTC. نمایش شمسی فقط در UI انجام می‌شود.

### پیامدها

- فنی: طراحی schema در فاز ۱ب با Prisma و همین مدل شروع می‌شود.
- امنیتی: دو لایه لازم است. ORM به‌تنهایی مرز tenant نیست.
- هزینه: یک خوشه‌ی PostgreSQL برای همه‌ی tenantها. عدد هزینه به ADR-004 وابسته است.
- زمان: فاز ۱ب به تأیید این ADR وابسته است. RLS خودش در فاز ۳ پیاده می‌شود.

### معیار بازبینی

اگر RLS داخل تراکنش Prisma عملی نباشد، ADR جدید باید جایگزین لایه‌ی دوم شود، نه لایه‌ی repository. اگر تعداد tenant یا نیاز انزوا از این مدل جلو بزند، schema یا DB جدا دوباره بررسی می‌شود.

## ADR-003: صف و پردازش پس‌زمینه

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

`SEC-005` می‌گوید webhook سریع `200` برمی‌گرداند و پردازش در صف انجام می‌شود. rate limit رسمی Meta هم صف و backoff می‌خواهد. سقف‌ها در بخش ۱۱ `03-instagram-api-constraints.md` است. نسخه‌ی دقیق Redis و BullMQ در 01b قفل می‌شود.

### گزینه‌ها

1. `BullMQ` روی `Redis`، با worker جدا در `apps/worker`
   - مزیت: rate limit، زمان‌بندی، retry و جدا بودن از فرایند وب.
   - عیب: یک فرایند و یک Redis بیشتر برای نگهداری.
2. `pg-boss`، صف روی Postgres
   - مزیت: ساده‌تر است و سرویس جدا نمی‌خواهد.
   - عیب: rate limiting و زمان‌بندی ضعیف‌تری دارد. این گزینه رد می‌شود.
3. سرویس مدیریت‌شده‌ی ابری
   - مزیت: نگهداری صف را بیرون می‌سپارد.
   - عیب: به محل میزبانی در ADR-004 وابسته است و آن ADR هنوز Proposed است. این گزینه رد می‌شود.

### تصمیم

- `BullMQ` روی `Redis` (حداقل 7). worker به‌صورت یک فرایند Node جدا (`apps/worker`) اجرا می‌شود.
- جریان webhook:
  1. Route Handler بدنه‌ی خام را می‌خواند.
  2. `X-Hub-Signature-256` را با مقایسه‌ی constant-time بررسی می‌کند.
  3. رویداد خام را با کلید idempotency یکتا (مثلاً `mid` یا comment id و نوع رویداد) در جدول `webhook_events` ذخیره می‌کند. unique constraint جلوی تکرار را می‌گیرد.
  4. job را enqueue می‌کند.
  5. سریع `200` برمی‌گرداند.
- صف‌های جدا: `webhooks-inbound`، `messages-outbound` (با rate limiter مطابق سقف‌های رسمی بخش ۱۱ سند `03`)، `tokens-refresh` (زمان‌بندی‌شده)، و `notifications`.
- retry با backoff نمایی و dead-letter. هیچ پیامی بیرون از پنجره‌ی مجاز Meta ارسال نمی‌شود و این شرط قبل از ارسال دوباره بررسی می‌شود.
- صف `tokens-refresh` همان توکن long-lived را با `ig_refresh_token` تمدید می‌کند. refresh token جداگانه وجود ندارد.

### پیامدها

- فنی: فاز ۱ب فقط worker خالی را می‌سازد. منطق webhook در فاز ۴ است.
- امنیتی: enqueue فقط بعد از امضای معتبر است. توکن در payload صف و لاگ نوشته نمی‌شود.
- هزینه: Redis کنار PostgreSQL. عدد هزینه به ADR-004 وابسته است.
- زمان: فاز ۴ و فاز ۵ به این ADR وابسته‌اند.

### معیار بازبینی

اگر Redis در محل میزبانیِ ADR-004 در دسترس نباشد، یا اگر rate limiter صف با سقف‌های رسمی Meta جور نشود.

## ADR-004: میزبانی و محل سرور

- وضعیت: Proposed
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS

### زمینه

سرور باید به `graph.instagram.com` و `graph.facebook.com` دسترسی پایدار داشته باشد و برای webhook نشانی HTTPS عمومی داشته باشد. اینکه این شرط از ایران برقرار است **تأییدنشده** است.

### گزینه‌ها

1. میزبانی در ایران
   - مزیت: هم‌مکانی با کاربر و درگاه ایرانی. این مزیت **استنباطی** از بازار هدف است و اندازه گرفته نشده است.
   - عیب: دسترسی پایدار به Graph API و رسیدن webhook از Meta **تأییدنشده** است.
2. میزبانی خارج از ایران
   - مزیت: در منبع این فاز، مزیت اثبات‌شده‌ای ثبت نشده است. همین شرط دسترسی و HTTPS برای این گزینه هم باید سنجیده شود.
   - عیب: اثر حقوقی داده، پرداخت، و پیامک کاربر ایرانی روی سرور خارج در این فاز بررسی نشده و **تأییدنشده** است.

### پیامدها

- فنی: بدون HTTPS عمومی، webhook و redirect ورود Meta قابل ثبت نیست.
- امنیتی: محل سرور روی دسترسی به secret و لاگ اثر می‌گذارد و هنوز ناشناخته است.
- هزینه: نامشخص.
- زمان: فاز ۲ به این ADR وابسته است و در صورت منفی بودن بررسی دسترسی، وضعیتش می‌تواند `مسدود` شود.

## ADR-005: مدل ورود به Meta

- وضعیت: Proposed
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS

### زمینه

سه مدل در سند رسمی آمده است. توصیه‌ی Meta برای پروژه‌ی جدید Unified Login است. یک اپ نمی‌تواند هم‌زمان Facebook Login و Instagram Login داشته باشد. توصیه، وضعیت این ADR را `Accepted` نمی‌کند. جزئیات در [مدل‌های اتصال](03-instagram-api-constraints.md#s2) است.

### گزینه‌ها

1. Unified Login
   - مزیت: توصیه‌ی Meta برای یکپارچه‌سازی جدید است. از `graph.facebook.com` استفاده می‌کند، توکن Business Integration System User می‌دهد، و به Page نیاز ندارد.
   - عیب: جزئیات اجرایی در این فاز پیاده نشده و تفاوت مجوزها با Instagram Login باید در App Review همان مسیر سنجیده شود.
2. Instagram API with Instagram Login
   - مزیت: از `graph.instagram.com` استفاده می‌کند، Instagram User token می‌دهد، و به Page نیاز ندارد.
   - عیب: جمع آن با Facebook Login در همان اپ مجاز نیست.
3. Facebook Login
   - مزیت: مسیر سند برای حساب متصل به Page است و پیام‌رسانی از Messenger Platform انجام می‌شود.
   - عیب: به Page نیاز دارد و جمع آن با Instagram Login در همان اپ مجاز نیست.

### تصمیم

### پیامدها

- فنی: مجوزها، میزبان Graph، و نوع توکن با این انتخاب عوض می‌شوند.
- امنیتی: عمر و روش تمدید توکن بین Instagram Login و Facebook Login یکی نیست. جزئیات در [توکن‌ها](03-instagram-api-constraints.md#s12) است.
- هزینه: نامشخص. App Review در هر سه مسیر برای کاربر واقعی لازم است.

## ADR-009: احراز هویت کاربران پنل

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تاریخ پذیرش: 1405/09/06 (2026-11-27)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS

### زمینه

پیوست قابلیت‌ها ورود MVP را OTP ثبت کرده است (`F-001`). الزام کوکی `HttpOnly` / `Secure` / `SameSite`، محدودیت نرخ، و CSRF در `SEC-012` است.

### گزینه‌ها

1. OTP موبایل
   - مزیت: با ردیف `F-001` هم‌خوان است و به بازار ایران نزدیک است. این نزدیکی **استنباطی** است.
   - عیب: به ADR-008 و تحویل پیامک وابسته است.
2. ایمیل و رمز
   - مزیت: به سرویس پیامک وابسته نیست.
   - عیب: با متن فعلی `F-001` یکی نیست و باید مالک محدوده را اصلاح کند.
3. هر دو
   - مزیت: کاربر بیش از یک راه ورود دارد.
   - عیب: دو مسیر بازیابی و دو مجموعه تست لازم است.

### تصمیم

ورود MVP فقط با OTP موبایل است. ایمیل و رمز برای V2 می‌ماند.

- شماره‌ی ایران `09xxxxxxxxx` به E.164 `+989xxxxxxxxx` نرمال می‌شود. شکل `+989xxxxxxxxx` هم پذیرفته است. شماره‌ی غیرایرانی رد می‌شود.
- نشست سمت سرور در جدول `Session` است. توکن خام در DB ذخیره نمی‌شود؛ فقط hash.
- کوکی `directora_session`: `HttpOnly`، `SameSite=Lax`، `Path=/`، و در production مقدار `Secure`.
- محافظت CSRF روی همه‌ی `/api/*` تغییردهنده (`POST` / `PATCH` / `DELETE`).
- OTP محدودیت نرخ و انقضا دارد.
- رابط `SmsProvider` قابل تعویض است. در dev/test مقدار `SMS_PROVIDER=console` است. اتصال Kavenegar، Melipayamak یا SMS.ir از طریق env برای بعد آماده می‌ماند و در این فاز پیاده یا انتخاب نمی‌شود.

### پیامدها

- فنی: پیاده‌سازی اختصاصی کوچک در `apps/web` است. Better Auth اجباری نیست.
- امنیتی: نرخ، انقضا، سقف تلاش، hash نشست و OTP، و CSRF روی متدهای تغییردهنده اعمال می‌شوند.
- هزینه: OTP هزینه پیامک دارد. تا انتخاب ADR-008 این هزینه نامشخص است.
- زمان: فرم ورود در همین فاز ساخته می‌شود.

### معیار بازبینی

قبل از فاز ۳. اگر روش غیر از OTP انتخاب شود، ردیف `F-001` در همان تصمیم به‌روز می‌شود.

## ADR-011: رمزنگاری توکن‌ها و مدیریت کلید

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تاریخ پذیرش: 1405/09/06 (2026-11-27)
- تصمیم‌گیرنده: مالک (Mamal) با پیشنهاد ATLAS

### زمینه

`SEC-002` رمزنگاری متقارن قوی را لازم کرده است. کلید باید بیرون دیتابیس باشد و بچرخد. توکن خام در لاگ و پاسخ نمی‌آید. در Instagram Login، refresh token جداگانه وجود ندارد. آنچه رمز می‌شود access token (long-lived) و هر توکن دیگری است که Meta صادر کند. ذخیره‌ی توکن Instagram در پرامپت بعدی است.

### گزینه‌ها

1. کلید در env، جدا از دیتابیس
   - مزیت: به سرویس خارجی وابسته نیست.
   - عیب: چرخش و توزیع کلید بین نمونه‌ها دستی‌تر است.
2. کلید در KMS
   - مزیت: چرخش و مرز دسترسی کلید را سرویس کلید انجام می‌دهد.
   - عیب: یک سرویس دیگر و وابستگی دسترسی به آن اضافه می‌شود. نام KMS در ورودی تسک نیست.

### تصمیم

رمزنگاری در حالت سکون AES-256-GCM است. کلید بیرون DB و در env است: `ENCRYPTION_KEY` و `ENCRYPTION_KEY_ID` نسخه‌دار. کنار هر ciphertext مقدار `keyId` ذخیره می‌شود تا چرخش کلید ممکن باشد. مهاجرت به KMS بعد از ADR-004 است و این مسیر بسته نیست. توکن یا کلید خام در لاگ و پاسخ API نمی‌آید.

### پیامدها

- فنی: هلپر `encryptSecret` / `decryptSecret` در `@directora/core` است. ذخیره‌ی توکن Instagram در پرامپت بعدی از همین هلپر استفاده می‌کند.
- امنیتی: کلید و plaintext در پیام خطا و لاگ نیستند.
- هزینه: env هزینه‌ی سرویس جدا ندارد. KMS بعد از ADR-004 هزینه دارد و عددش نامشخص است.
- زمان: هلپر در همین فاز است. ذخیره‌ی توکن واقعی با اتصال Meta است.

### معیار بازبینی

قبل از فاز ۴، و هنگام اولین چرخش کلید.

## ADR-012: ساختار مخزن

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

کد بعدی در همین Root می‌ماند. ADR-001 مدیر بسته را `pnpm` با workspaces کرده است. پوشه‌های `apps/` و `packages/` در این تسک ساخته نمی‌شوند. 01b آن‌ها را می‌سازد.

### گزینه‌ها

1. یک مخزن، monorepo با `pnpm` workspaces و `Turborepo`، و worker جدا
   - مزیت: سند، قانون و کد در یک تاریخچه می‌مانند و پردازش صف از فرایند وب جدا است.
   - عیب: مرز وابستگی بین packageها باید صریح بماند.
2. تک‌اپ Next.js بدون worker جدا
   - مزیت: یک فرایند برای استقرار اولیه.
   - عیب: پردازش صف داخل فرایند وب برای webhook و rate limit قابل‌اتکا نیست. این گزینه رد می‌شود.
3. چند مخزن
   - مزیت: چرخه‌ی انتشار هر بخش جدا می‌شود.
   - عیب: ADR و قانون امنیتی از کد عقب می‌مانند. این گزینه رد می‌شود.

### تصمیم

یک مخزن (همین Root)، به‌صورت monorepo با `pnpm` workspaces و `Turborepo`. ساختاری که 01b می‌سازد:

```
apps/
  web/          # Next.js: سایت معرفی + پنل کاربر + Super Admin + Route Handlers (webhook، callbackها)
  worker/       # Node + BullMQ: پردازش webhook، ارسال پیام، تمدید توکن
packages/
  ui/           # کامپوننت‌ها و design tokens (منبع واحد ظاهر)
  db/           # Prisma schema، migration، client و repositoryهای tenant-safe
  core/         # منطق دامنه: قواعد اتوماسیون، تطبیق کلمه، پنجره‌ی ۲۴ ساعته (بدون وابستگی به Next)
  instagram/    # کلاینت Graph API رسمی، امضای webhook، typeهای payload
  config/       # eslint، tsconfig و prettier مشترک
docs/  .cursor/
```

قانون وابستگی: `apps/*` می‌تواند از `packages/*` استفاده کند. `packages/core` به هیچ فریم‌ورکی وابسته نیست. `packages/ui` به `db` یا `instagram` وابسته نیست.

### پیامدها

- فنی: 01b همین درخت را می‌سازد. تا آن تسک این پوشه‌ها وجود ندارند.
- امنیتی: منطق پنجره‌ی پیام و تطبیق در `packages/core` می‌ماند تا بدون Next قابل تست باشد.
- هزینه: هزینه‌ی مخزن جدا ندارد.
- زمان: فاز ۱ب به تأیید این ADR وابسته است.

### معیار بازبینی

اگر وابستگی ممنوع بین `packages/ui` و `packages/db` یا `packages/instagram` در عمل لازم شد، اول ADR جدید، بعد تغییر ساختار.

- فنی: سندها، پکیج‌های `@directora/*` و wordmark از همین نام استفاده می‌کنند. دامنه در ADR-016 می‌ماند.
- امنیتی: این ADR به کوکی یا callback مربوط نیست.
- هزینه: شباهت نام «دایرکتورا» با رقیب «دایرکتام» تأییدنشده است. بررسی ثبت علامت تجاری و احتمال اشتباه گرفتن دو برند پیش از انتشار عمومی لازم است.
- زمان: فاز ۲ب و فاز ۸ برای دامنه به ADR-016 وابسته‌اند، نه به این ADR.

### معیار بازبینی

قبل از انتشار عمومی، اگر نتیجه‌ی بررسی علامت تجاری منفی باشد. تغییر نام فقط با ADR جدید انجام می‌شود.

## ADR-015: پشته‌ی UI و سیستم طراحی

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

مالک کیفیت UI را الزام پذیرش می‌داند: محصول باید زیبا، حرفه‌ای و premium باشد و هویت مستقل داشته باشد. پالت Directam ماژنتا است و پالت ما نباید ماژنتا یا صورتی باشد. پالت محصول پالت لوگوی دایرکتورا (`blue`، `cyan`، `ink`، `orange`، `amber`) است. مقدار توکن‌ها در `docs/09-design-system.md` است. نسخه‌ی دقیق پکیج‌ها در ADR-017 قفل شده است.

### گزینه‌ها

1. `Tailwind CSS` 4، توکن CSS، الگوی `shadcn/ui` روی `Radix UI`، و کتابخانه‌های فهرست‌شده در تصمیم
   - مزیت: توکن‌ها منبع واحد ظاهرند، primitiveها دسترس‌پذیرند، و ظاهر پیش‌فرض یک کتابخانه‌ی سنگین تحمیل نمی‌شود.
   - عیب: کامپوننت shadcn باید با توکن‌های خودمان بازطراحی شود و ظاهر پیش‌فرضش استفاده نمی‌شود.
2. `MUI` یا `Ant Design`
   - مزیت: مجموعه‌ی آماده‌ی کامپوننت.
   - عیب: هویت ظاهری قوی و سنگین که شخصی‌سازی premium را سخت می‌کند. این گزینه رد می‌شود.
3. CSS-in-JS در زمان اجرا
   - مزیت: استایل کنار کامپوننت است.
   - عیب: با Server Components سازگاری ضعیفی دارد. این گزینه رد می‌شود.

### تصمیم

- `Tailwind CSS` نسخه‌ی 4، با توکن‌ها به‌صورت CSS variables که در `@theme` تعریف می‌شوند. منبع واحد توکن‌ها `packages/ui` است.
- کامپوننت‌ها: الگوی `shadcn/ui` روی primitiveهای دسترس‌پذیر `Radix UI`. کد کامپوننت داخل `packages/ui` نگه داشته می‌شود و با توکن‌های ما بازطراحی می‌شود. ظاهر پیش‌فرض shadcn مستقیم استفاده نمی‌شود.
- آیکون: `lucide-react`. آیکون‌های جهت‌دار در RTL آینه می‌شوند.
- نمودار: `Recharts` (از طریق الگوی chart در shadcn) با رنگ‌های `chart-1..6`.
- انیمیشن: `motion` (Framer Motion)، فقط با توکن‌های motion، و با رعایت `prefers-reduced-motion`.
- فرم: `react-hook-form` + `zod`.
- جدول: `@tanstack/react-table`.
- Toast: `sonner`.
- تاریخ شمسی: `date-fns-jalali` یا `Intl.DateTimeFormat('fa-IR-u-ca-persian')`. انتخاب نهایی در 01b و پیچیده‌ترین فرمت‌ها با تست بررسی می‌شوند.
- فونت: `Vazirmatn` (مجوز SIL Open Font License 1.1)، self-host با `next/font/local`، بدون CDN. فونت mono برای شناسه‌ها و کد: `JetBrains Mono` (OFL).
- Dark mode: `next-themes` با کلاس `dark`. حالت پیش‌فرض تابع سیستم است.

### پیامدها

- فنی: 01b توکن‌های `09-design-system.md` را به CSS variables ترجمه می‌کند و فونت را self-host می‌کند.
- امنیتی: فونت از CDN بارگذاری نمی‌شود.
- هزینه: کتابخانه‌های نام‌برده هزینه‌ی سرویس جدا ندارند. مجوز فونت‌ها OFL است.
- زمان: هر صفحه‌ی UI بعد از وجود `packages/ui` ساخته می‌شود، نه قبل از آن.

### معیار بازبینی

اگر Tailwind 4 مدل `@theme` را طوری عوض کند که توکن‌های سند طراحی قابل نگاشت نباشند، یا اگر انتخاب بین `date-fns-jalali` و `Intl` در تست 01b شکست بخورد. تغییر رنگ برند فقط با عوض کردن توکن‌ها است. تغییر نام برند ADR جدید می‌خواهد.

   - عیب: تغییر بعدی دامنه روی اپ ثبت‌شده‌ی Meta هزینه دارد. این هزینه در منبع عددی ندارد.

## ADR-017: نسخه‌های پین‌شده و ابزارهای اسکلت

- وضعیت: Accepted
- تاریخ: 1405/09/04 (2026-11-25)
- تصمیم‌گیرنده: مالک (Mamal)، با پیشنهاد ATLAS برای جزئیات

### زمینه

اسکلت monorepo بدون نسخه‌ی قفل‌شده قابل بازتولید نیست. ناظر این نسخه‌ها را در ۱۴۰۵/۰۹/۰۴ از npm registry بررسی کرده است. تگ `latest` برای Prisma روی نسخه‌ی rc است و برای انتخاب نسخه کافی نیست.

### گزینه‌ها

1. نسخه‌های exact همین جدول، با استثناهای سازگاری زیر
   - مزیت: نصب تکرارپذیر است و peer dependencyهای شناخته‌شده عمداً دور زده نمی‌شوند.
   - عیب: ارتقای major بعداً ADR جدید می‌خواهد.
2. بازه‌ی `^` یا `~`، یا دنبال کردن تگ `latest`
   - مزیت: به‌روزرسانی جزئی خودکار است.
   - عیب: یک نصب بعدی می‌تواند Prisma 8-rc یا TypeScript 7 را بیاورد و اسکلت را بشکند. این گزینه رد می‌شود.
